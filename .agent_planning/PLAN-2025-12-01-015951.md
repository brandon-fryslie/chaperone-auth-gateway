## Phase 3: Secret Management (P0/P1 - 7 items)

Phase 3 builds the credential retrieval system that fetches secrets from various backends without exposing them to applications.

**Status:** Not Started

**Dependencies:** None (CHAP-dhf already defines interface in Phase 0.1)
**Spec Reference:** PROJECT_SPEC.md §88-97 (Secret Providers), §186-194 (credential_ref format)
**Status Reference:** STATUS-2025-12-01-015951.md (Phase 3 Preview)

##### Description
Build the foundational secret provider infrastructure including credential_ref parser (splits "protocol:path" format), provider registry, and convenience Fetch() function. This is the foundation that all secret providers depend on.

##### Acceptance Criteria
- [ ] credential_ref parser splits "env:OPENAI_API_KEY" → protocol="env", path="OPENAI_API_KEY"
- [ ] credential_ref parser splits "file:/path/to/secret.txt" → protocol="file", path="/path/to/secret.txt"
- [ ] Parser handles edge cases (missing colon, multiple colons, empty protocol/path)
- [ ] Provider registry stores and retrieves providers by protocol name
- [ ] `Register(name string, provider SecretProvider)` function works
- [ ] `Get(protocol string) (SecretProvider, error)` function returns correct provider
- [ ] `Fetch(ctx context.Context, ref string) (string, error)` convenience function:
  - Parses credential_ref
  - Gets provider from registry
  - Calls provider.Fetch()
  - Returns secret or error
- [ ] Unit tests cover all parser edge cases
- [ ] Unit tests verify registry operations
- [ ] Integration test validates full Fetch() flow
- [ ] go test -race passes (no concurrent access issues)

##### Technical Notes
- Use sync.RWMutex for registry to allow concurrent reads
- credential_ref format: `protocol:path` where protocol is alphabetic [a-z]+
- Parser should handle file paths with colons (e.g., "file:C:/path" on Windows)
- Error types (ErrSecretNotFound, ErrPermissionDenied, ErrTimeout) defined in Phase 0.2

### P1: File-Based Provider

#### CHAP-2iw: file: Secret Provider with Permission Checks
**Status:** Not Started
**Effort:** Medium (3-5 days)
**Dependencies:** CHAP-txf (provider registry)
**Spec Reference:** PROJECT_SPEC.md §92 (file: provider), §188 (example credential_ref)
**Status Reference:** STATUS-2025-12-01-015951.md (Phase 3 Goals)

##### Description
Implement file-based secret provider with strict permission enforcement (0600 or stricter required). This provider reads secrets from local files while ensuring they're not world-readable.

##### Acceptance Criteria
- [ ] `file:/path/to/secret` reads file content using os.ReadFile()
- [ ] Files with 0600 (rw-------) permissions work
- [ ] Files with 0400 (r--------) permissions work
- [ ] Files with 0644 (rw-r--r--) permissions rejected with ErrPermissionDenied
- [ ] Files with 0666 permissions rejected with ErrPermissionDenied
- [ ] Missing files return ErrSecretNotFound
- [ ] File size limit enforced (max 1MB)
- [ ] Files larger than 1MB rejected with appropriate error
- [ ] Whitespace (leading/trailing) trimmed from file content
- [ ] Empty files (after trim) return ErrSecretNotFound
- [ ] Symbolic links followed (permission check on target file)
- [ ] Provider registered automatically in init()
- [ ] Unit tests cover all permission scenarios (0400, 0600, 0644, 0666, 0777)
- [ ] Unit tests verify file size limit
- [ ] Unit tests verify whitespace trimming
- [ ] Integration test validates full file reading flow

##### Technical Notes
- Use os.Stat() to check permissions before reading
- Check `fileInfo.Mode() & 0077` - if non-zero, file is too permissive
- Use os.ReadFile() for atomic read
- Respect context cancellation
- Consider race condition: file permissions could change between stat and read
- Solution: stat → read → verify content is non-empty (don't re-stat)

**Status:** Not Started

##### Description
Implement secret caching layer with 5-minute TTL to reduce provider calls while allowing rotation. This wraps all providers and provides ~80% hit rate for typical usage.

##### Acceptance Criteria
- [ ] CachedProvider wrapper implemented
- [ ] sync.Map used for concurrent access (not regular map + mutex)
- [ ] Cache entries store: (secret string, expireAt time.Time)
- [ ] Fetch() checks cache first, returns if not expired
- [ ] Fetch() calls underlying provider if expired or missing
- [ ] Fetch() caches successful results with 5-minute TTL
- [ ] TTL is configurable (default: 5 minutes)
- [ ] Cache invalidation function: `Invalidate(ref string)` clears entry
- [ ] Cache clear function: `Clear()` removes all entries
- [ ] Cache stats available: Hits(), Misses(), Size()
- [ ] All providers automatically wrapped with caching
- [ ] Unit tests verify TTL behavior (mock time.Now)
- [ ] Unit tests verify cache hit/miss logic
- [ ] Unit tests verify concurrent access (go test -race)
- [ ] Load test: 1000 concurrent requests hit cache correctly
- [ ] Integration test shows cache reduces provider calls by ~80%

##### Technical Notes
- Use sync.Map for lockless reads on cache hits
- Cache key should be full credential_ref (e.g., "env:OPENAI_API_KEY")
- Store errors in cache too (with shorter TTL: 30 seconds) to avoid hammering failing providers
- Consider negative caching for ErrSecretNotFound (prevents repeated stat calls for missing files)
- Eviction: No active eviction needed (entries expire lazily on next Fetch)
- Memory bound: Add max size limit (e.g., 1000 entries) with LRU eviction if needed

##### Description
Wire service engine, secret providers, and auth strategies into MITM request handler to create complete credential injection flow.

##### Acceptance Criteria

- [ ] Secret fetched using secrets.Fetch(ctx, service.CredentialRef)
- [ ] Auth strategy selected based on service.AuthStrategy
- [ ] Strategy.Apply(req, secret) modifies request
- [ ] Policies enforced before forwarding request:
  - Method allowlist checked
  - Path allowlist checked
  - Body size limit enforced
- [ ] Correct error responses for each failure mode:
  - 403 if policy denies request
  - 503 if secret fetch fails
  - 502 if upstream connection fails
  - 500 for internal errors
- [ ] All decisions logged with structured logging
- [ ] Request ID propagated through entire flow
- [ ] Edge cases handled gracefully:
  - Service not found (pass through as tunnel)
  - Secret provider not found (503)
  - Auth strategy not found (500)
  - Network errors (502)
- [ ] Integration test validates full flow:
  - Configure service with env: credential_ref
  - Set environment variable
  - Send request through proxy
  - Verify Authorization header injected
  - Verify upstream receives authenticated request
- [ ] Integration test validates policy enforcement in full flow
- [ ] Integration test validates error responses
- [ ] Load test: 100 concurrent requests with credential injection

##### Technical Notes
- Order of operations critical:
  1. MITM TLS handshake
  2. Receive HTTP request
  3. Look up service by hostname
  4. Enforce policy (return 403 if denied)
  5. Fetch secret (return 503 if fails)
  6. Get auth strategy (return 500 if not found)
  7. Clone request
  8. Apply auth strategy
  9. Establish upstream TLS
  10. Forward request
  11. Proxy response
- Error handling must not leak sensitive information
- Logging must not log secret values
- Request ID must appear in all log lines for traceability
