## Risk Assessment

### Technical Risks

#### 1. TLS MITM Complexity (VERY HIGH RISK)

**Risk:** Dynamic certificate generation, CA management, and client trust is non-trivial. Certificate validation and system trust store integration vary significantly across platforms (macOS vs Linux vs Windows).

**Impact:** If MITM doesn't work correctly, entire system fails. Users unable to trust CA means proxying fails.

**Likelihood:** HIGH (TLS is complex, easy to make mistakes)

**Mitigation:**
- Use well-tested libraries (stdlib crypto/x509, crypto/tls)
- Follow established patterns (study mitmproxy, Burp Suite architecture)
- Extensive testing with real browsers and HTTPS clients
- Clear documentation on CA trust installation per platform
- Provide troubleshooting guide for common cert issues
- Consider using existing cert generation library (like mkcert logic)

#### 2. Streaming Backpressure (HIGH RISK)

**Risk:** HTTP streaming with proper backpressure requires careful buffer management. Easy to introduce memory leaks (buffering entire response) or deadlocks (circular buffer dependencies).

**Impact:** Large responses could cause OOM. Slow readers could hang connections.

**Likelihood:** MEDIUM (io.Copy handles most cases, but edge cases exist)

**Mitigation:**
- Use io.Copy for all streaming (proven implementation)
- Avoid any buffering between inbound and outbound
- Test with multi-GB responses
- Test with slow readers (artificial delays)
- Monitor memory usage during streaming tests
- Use context cancellation to prevent goroutine leaks

#### 3. Concurrency Safety (HIGH RISK)

**Risk:** Proxy handles many concurrent requests. Shared state (service registry, secret cache, OAuth2 token cache) must be goroutine-safe. Data races are easy to introduce.

**Impact:** Data races cause undefined behavior, crashes, or security vulnerabilities (e.g., wrong secret sent to wrong service).

**Likelihood:** MEDIUM (Go makes concurrency easy but not foolproof)

**Mitigation:**
- Minimize shared mutable state
- Use sync.Map, sync.RWMutex where needed
- Run all tests with -race flag
- Use immutable service registry (replace on reload, don't mutate)
- Document concurrency assumptions in code comments
- Use go vet and golangci-lint to catch common mistakes

#### 4. Enterprise Proxy Compatibility (MEDIUM RISK)

**Risk:** Spec claims Zscaler compatibility, but outbound HTTPS through corporate MITM proxies may have edge cases (cert pinning, protocol restrictions, auth requirements).

**Impact:** Chaperone doesn't work in enterprise environments, reducing adoption.

**Likelihood:** MEDIUM (most corporate proxies are compatible, but edge cases exist)

**Mitigation:**
- Test with real corporate proxy (Zscaler, Proxy, etc.) if possible
- Support HTTP_PROXY env var for outbound connections
- Document corporate proxy setup in docs
- Provide troubleshooting guide for proxy issues
- Consider proxy authentication (Basic, NTLM) in future phase

#### 5. Secret Provider Reliability (MEDIUM RISK)

**Risk:** External secret stores (Vault, Keychain, command execution) introduce failure modes. Vault server down, Keychain locked, command times out, etc.

**Impact:** API calls fail even though application and API are both healthy. Poor error messages confuse users.

**Likelihood:** MEDIUM (external dependencies always fail eventually)

**Mitigation:**
- Implement clear error types (ErrVaultUnreachable, ErrKeychainLocked, etc.)
- Return helpful error messages to client (without leaking secrets)
- Log detailed errors server-side
- Implement retry logic for transient failures (with exponential backoff)
- Document failure modes and troubleshooting per provider
- Consider fallback providers (primary + backup)

#### 6. Platform-Specific Keychain Integration (HIGH RISK)

**Risk:** macOS Keychain, gnome-keyring, and kwallet have different APIs, behaviors, and failure modes. Testing across platforms is complex.

**Impact:** Keychain provider works on macOS but fails on Linux or vice versa.

**Likelihood:** HIGH (platform-specific code always has portability issues)

**Mitigation:**
- Use cross-platform library (github.com/99designs/keyring)
- Test on macOS, Ubuntu (gnome-keyring), and Fedora (kwallet)
- Document platform-specific setup per OS
- Provide fallback to file: or env: if keychain unavailable
- Consider making keychain: optional (not in MVP)

### Security Risks

#### 1. Local CA Trust (VERY HIGH RISK)

**Risk:** Getting users to trust the local CA is a UX and security challenge. If CA private key is compromised, attacker can MITM all traffic. Malware could exploit trusted Chaperone CA.

**Impact:** Compromised CA key allows attacker to intercept all HTTPS traffic from user's machine. Security model broken.

**Likelihood:** MEDIUM (if CA key stored with correct permissions, risk is reduced)

**Mitigation:**
- Store CA private key with 0600 permissions (user-only read/write)
- Store CA private key in secure location (`~/.config/chaperone/`, not world-readable)
- Generate unique CA per user (don't share CA across users)
- Document CA trust implications (user trusting local proxy)
- Provide CA revocation instructions (remove from system trust store)
- Consider passphrase-protecting CA private key (advanced)
- Log all cert generations for audit trail
- Set short CA validity (1 year, require regeneration)

#### 2. Secret Leakage (VERY HIGH RISK)

**Risk:** Any bug in secret provider code could leak credentials to logs, memory dumps, error messages, or HTTP responses.

**Impact:** Secrets exposed, defeating entire purpose of Chaperone.

**Likelihood:** MEDIUM (careful coding reduces risk, but bugs happen)

**Mitigation:**
- NEVER log secret values (log "fetched secret from env:OPENAI_API_KEY" not "fetched secret: sk-...")
- Sanitize error messages (don't include secret in error.Error())
- Redact Authorization headers in audit logs (log "Authorization: Bearer [REDACTED]")
- Use secure memory if possible (mlock, zero on cleanup)
- Run static analysis to detect accidental logging
- Code review all secret handling code
- Test: inject invalid secret, verify error message doesn't contain secret

#### 3. Audit Log Integrity (MEDIUM RISK)

**Risk:** If audit logs can be tampered with, security value is reduced. Attacker could delete evidence of unauthorized access.

**Impact:** Security incidents undetectable, compliance requirements not met.

**Likelihood:** LOW (local filesystem permissions usually sufficient)

**Mitigation:**
- Write audit logs to append-only file (if supported by filesystem)
- Set restrictive permissions on log files (0600)
- Consider remote logging (syslog, OpenTelemetry) for tamper-resistance
- Document log integrity requirements
- Implement log signing (HMAC of each log line) in future phase

#### 4. Policy Bypass (HIGH RISK)

**Risk:** Bugs in policy enforcement could allow unauthorized API access. Path matching edge cases, method checking, etc.

**Impact:** Applications can call disallowed API endpoints, violating intended access control.

**Likelihood:** MEDIUM (policy logic is complex, edge cases exist)

**Mitigation:**
- Use well-tested glob matching library (or regex)
- Write comprehensive tests (allowed paths, denied paths, edge cases like `/v1/../admin`)
- Default to deny (if no policy matches, deny)
- Log all policy denials for audit

#### 5. Certificate Validation (VERY HIGH RISK)
