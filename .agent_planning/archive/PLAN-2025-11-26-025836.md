The minimum viable product (MVP) requires completing the critical path:

With supporting work from Phase 6 (configuration) and Phase 7 (testing).

**MVP Success Criteria:**
1. Binary successfully proxies HTTPS CONNECT tunnels for arbitrary domains (transparent tunnel)
2. Binary performs selective MITM for one configured domain (e.g., api.openai.com)
3. Bearer token from `env:` provider is injected into requests

7. Local CA certificate can be generated and trusted by user
8. Configuration loaded from TOML file
9. `chaperone run` starts the proxy
10. `chaperone init openai` generates example config

**Out of Scope for MVP:**
- Advanced secret providers (keychain:, command:, vault:) - only env: and file: for MVP
- Advanced auth strategies (HMAC, SigV4, OAuth2) - only bearer and header for MVP
- Client identification and ACL
- Rate limiting
- Advanced logging (file rotation, syslog, OpenTelemetry) - only stdout for MVP
- Hot reload
- Unix domain sockets
- Comprehensive documentation (only README and basic examples)

## Risk Assessment

### Very High Risk Items

1. **TLS MITM Complexity** (Phase 2)
   - Dynamic certificate generation and CA management is non-trivial
   - Certificate validation and trust varies across platforms (macOS, Linux, Windows)
   - Mitigation: Use well-tested libraries, extensive testing, clear documentation

2. **Local CA Trust** (Phase 2)
   - Getting users to trust CA is UX challenge
   - Compromised CA key allows MITM of all traffic
   - Mitigation: 0600 permissions on CA key, unique CA per user, clear trust instructions

3. **Secret Leakage** (Phase 3)
   - Any bug could leak credentials to logs, error messages, or HTTP responses
   - Mitigation: NEVER log secret values, sanitize errors, redact auth headers in logs

### High Risk Items

4. **Streaming Backpressure** (Phase 1, Phase 2)
   - Large responses could cause OOM without proper backpressure
   - Mitigation: Use io.Copy (proven), test with multi-GB responses, monitor memory

5. **Concurrency Safety** (All phases)
   - Shared state (service registry, secret cache) must be goroutine-safe
   - Data races cause undefined behavior or security vulnerabilities
   - Mitigation: Minimize shared state, use sync.Map/sync.RWMutex, run tests with -race

6. **Certificate Validation** (Phase 2)
   - Improper outbound validation enables MITM attacks on Chaperone itself
   - Mitigation: NEVER set InsecureSkipVerify, use system cert pool, test with invalid certs

7. **Policy Bypass** (Phase 5)
   - Bugs in policy enforcement allow unauthorized API access
   - Mitigation: Comprehensive tests, default to deny, log all denials

### Medium Risk Items

8. **Enterprise Proxy Compatibility** (Phase 2)
   - Outbound HTTPS through corporate MITM proxies may have edge cases
   - Mitigation: Support HTTP_PROXY env var, test with real corporate proxy if possible

9. **Secret Provider Reliability** (Phase 3)
   - External secret stores (Vault, Keychain) introduce failure modes
   - Mitigation: Clear error types, helpful error messages, retry logic

10. **Configuration Complexity** (Phase 6)
    - Users must understand service configs, auth strategies, credential_refs
    - Mitigation: Excellent documentation, `chaperone init` templates, clear error messages
