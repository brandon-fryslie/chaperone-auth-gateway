# Distillation: Chaperone Auth Gateway
Timestamp: 2026-01-16-141341
Scope: Entire codebase (~8,600 LOC in 60+ source files)

## The Essence

**In one sentence**: A MITM proxy that intercepts HTTPS connections, strips any existing auth headers from requests, and injects the correct credentials - so applications never handle secrets directly.

**Core concepts** (the load-bearing abstractions):

1. **Service**: A configured API endpoint (host pattern) with its auth strategy, credential reference, and access policy. Lives in `internal/service/registry.go`. Everything flows from this: which requests to intercept, how to authenticate them, what constraints to enforce.

2. **Credential Injection Pipeline**: The handler chain in `internal/proxy/handlers.go` that transforms requests: connect → requestID → drop → securityStripAuth → policy → strip → auth → record. Each stage is a pure function `(request, ctx) → (request, response)`.

3. **Secret Provider**: The pluggable `Provider` interface (`internal/secrets/registry.go`) that fetches credentials from env vars, files, or keychain. Format: `env:VAR_NAME`, `file:/path`, `keychain:service/account`.

4. **Auth Strategy**: The pluggable `AuthStrategy` interface (`internal/auth/strategy.go`) that applies credentials to requests. Currently: bearer token, custom header. Strategies are stateless and concurrent-safe.

5. **Run Mode Lifecycle**: `internal/run/` orchestrates spawning a child process with proxy environment injected, ephemeral CA, signal forwarding, and coordinated shutdown. This is how Chaperone becomes invisible to the application.

## Where Essence Is Strong

**The handler chain** (`handlers.go:157-183`): The request pipeline is explicit, ordered, and each handler has a single responsibility. The ordering (strip first, inject second) is correct and well-documented.

**Secret abstraction** (`secrets/registry.go`): Clean separation between "how to reference a secret" (the `provider:path` format) and "how to fetch it" (Provider interface). Adding a new secret source requires only implementing `Fetch(ctx, path)`.

**Service registry matching** (`service/registry_impl.go`): Hostname normalization, wildcard matching, case-insensitive lookup - all in one place. The interface is minimal: Register, Lookup, ListAll.

**Ephemeral CA in run mode** (`cmd/run.go:159-187`): Fresh CA per invocation, stored in `/tmp/chaperone-ca-<pid>/`, auto-cleaned on exit. No system trust required. Security model is sound.

## Where Essence Is Diluted

### Scattered

| Concept | Expressions | Files |
|---------|-------------|-------|
| Config loading | `config.Load()`, `config.LoadWithMerge()` | `config/config.go`, `config/merge.go` |
| Header stripping | `knownAuthHeaders` list, `stripHandler()`, `securityStripAuthHandler()` | `handlers.go:240-388` |
| Proxy mode setup | `runInject()`, `runWithProxy()`, `runExamine()`, `runInit()` | 4 separate cmd files, each 200-450 lines |

### Overloaded

| Component | Responsibilities | Should Be |
|-----------|------------------|-----------|
| `handlers.go` (803 LOC) | CONNECT handling, 8 request handlers, 3 response handlers, request metadata, credential redaction, init mode handlers, examine mode handlers | Split: core pipeline vs mode-specific handlers |
| `cmd/inject.go` (450 LOC) | CLI parsing, config loading, service registration, strategy registration, secret preloading, validation, server startup | CLI layer should be thin; push orchestration to internal |
| `cmd/run.go` (402 LOC) | Same as inject + ephemeral CA, env building, process spawning, signal forwarding | Similar split needed |

### Obscured

| What | Where It Hides | Its True Nature |
|------|----------------|-----------------|
| The "strip existing auth before inject" invariant | `securityStripAuthHandler()` | Core security property, not just "a handler" |
| Placeholder authentication (Layer 2 security) | Scattered in `authHandler()` checks | A distinct security boundary deserving explicit representation |
| The request pipeline ordering contract | Comments in `server.go:159-183` | Should be enforced structurally, not just documented |

## The Implied Architecture

**Current shape**:
```
cmd/
  inject.go    [CLI + all orchestration]
  run.go       [CLI + all orchestration + process mgmt]
  examine.go   [CLI + minimal orchestration]
  check.go     [purely informational]

internal/
  proxy/       [handlers.go is a monolith]
  service/     [clean]
  secrets/     [clean]
  auth/        [clean]
  run/         [clean]
  init/        [separate feature, well-isolated]
  examine/     [separate feature, well-isolated]
```

**Natural shape**:
```
cmd/           [thin CLI layer - flag parsing only]

internal/
  orchestrate/ [NEW: wire up modes - inject, run, examine]
  pipeline/    [NEW: the request handler chain, explicit ordering]
  proxy/       [just server start/stop, connection handling]
  service/     [unchanged]
  secrets/     [unchanged]
  auth/        [unchanged]
  run/         [unchanged]
```

**Tension points**:
- `inject.go` and `run.go` share 80% of their setup code but aren't factored together
- `handlers.go` grew organically as features were added; no clear boundary between "core pipeline" and "mode-specific"
- The `init/` package is feature-complete and isolated, showing what clean separation looks like

## The Stranger Test

If I had 5 minutes to explain this codebase:

"Chaperone is a local HTTPS proxy that injects API credentials. You configure which hosts need auth (`api.openai.com`), what credentials to use (`env:OPENAI_API_KEY`), and how to apply them (`bearer` token).

When you run `chaperone run openai -- python script.py`, it:
1. Starts a proxy on a Unix socket
2. Generates an ephemeral CA certificate
3. Spawns your script with `HTTPS_PROXY` pointed at the socket
4. Intercepts matching HTTPS traffic via MITM
5. Strips any existing auth headers (security: prevents credential leakage)
6. Injects the configured credentials
7. Forwards to the real API

The key files are `internal/proxy/handlers.go` (the request pipeline) and `internal/service/registry.go` (which hosts to intercept).

There are additional modes: `inject` (long-running server), `examine` (auth discovery), `init` (wizard for config generation), `check` (security audit)."

**What I'd skip**: The init wizard, HAR recording, examine mode, audit logging, the colored terminal output. These are features, not essence.

**What I'd apologize for**:
- "The cmd files are pretty long - they should be thinner, with orchestration pushed down"
- "handlers.go is doing too much - it's 800 lines and growing"
- "There's some duplication between inject.go and run.go in how they set up registries"

## For the Practitioner

This distillation is a seeing, not a prescription.

**If proceeding to prune**:
- The `init/` package is self-contained; if that feature isn't used, it can be removed cleanly
- HAR recording (`recorder/har.go`) could be optional/pluggable
- The colored log handler is 600 lines for aesthetics

**If proceeding to hone**:
- Extract a `Pipeline` type from `handlers.go` that makes ordering explicit
- Factor common setup from `inject.go` and `run.go` into `internal/orchestrate`
- The `placeholder` authentication check deserves to be a first-class concept, not buried in `authHandler()`

**If setting this aside**: The codebase is functional and maintainable at current scale. The dilution is not blocking work; it's making future growth harder. Return when adding the next major feature.
